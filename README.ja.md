# 🔄 DevLoop

> 要件を一つ入力するだけで、検証済み・スペック駆動・アーカイブ済みの変更が完成します。

[English](README.md) | [中文](README.zh-CN.md) | **[日本語](README.ja.md)**

DevLoop は、[要件のヒアリング](https://github.com/mattpocock/skills)、[OpenSpec](https://github.com/Fission-AI/OpenSpec) スペック駆動開発、TDD、コードレビュー、アーカイブを統合した**自動化開発ループ**です 🚀

開発ライフサイクル全体で複数のツールを手動で調整する代わりに、要件を一つ提供するだけで、DevLoop がプロセス全体を駆動します——明確化、探索、仕様化、実装、テスト、検証、アーカイブまで。

---

## 🤔 なぜ DevLoop が必要か？

AI コーディングエージェントは強力ですが、予測不能な面もあります。よくある失敗パターン：

| 失敗 | 原因 | DevLoop の解決策 |
|------|------|-----------------|
| 間違ったものを作る | 認識のズレ | 🔍 コード前にヒアリングセッション |
| スパゲッティコード | アーキテクチャ規律なし | 📐 スペックファースト原則 + モジュール仕様追跡 |
| 決定事項が不明 | チャット履歴にだけ残る | 📄 OpenSpec アーティファクトを永続的な真実として保存 |
| スペックとコードの乖離 | 検証ステップなし | ✅ アーカイブ前の三層検証 |
| 小さな修正に過剰なドキュメント | 一律プロセス | ⚖️ リスクベースルーティング（L0-L3） |
| 中断で作業ロスト | セッションのみの状態 | 💾 変更ごとの状態ファイル（`devloop/.state/`）でセッション横断復旧 |

## ⚙️ 仕組み

```text
ユーザー: /develop ダークモードサポートを追加したい

DevLoop:
  1. プロジェクトコンテキストを読み込み（設定、アーキテクチャマップ、ドメイン言語）
  2. リスク分類 → L2（中機能）
  3. 影響するモジュールを探索、欠落スペックを構築
  4. ユーザーにヒアリングし、すべての決定分岐を明確化
  5. OpenSpec チェンジを作成（proposal + specs + design + tasks）
  ── ⏸️ ユーザーが要件理解を確認 ──
  ── ⏸️ ユーザーが計画とスペックを確認 ──
  6. TDD で実装（レッド-グリーン-リファクタ）
  7. スペックのギャップ？→ まず OpenSpec を更新、それからコード
  8. テスト、型チェック、Lint を実行
  9. /opsx:verify を実行（スペックの完全性・正確性・整合性）
 10. コードレビューを実行（標準 + スペック準拠）
  ── ⏸️ ユーザーがアーカイブを確認 ──
 11. スペックを正式レジストリに同期
 12. チェンジをアーカイブ
 13. モジュールインデックスとアーキテクチャマップを更新
 14. デリバリーレポートを出力 📦
```

## 🛠️ 二つの Skill

### `devloop-setup` — 初期化

任意のリポジトリで DevLoop ワークフローを設定・確認・修復します。

```text
/devloop-setup              # ステータス確認（デフォルト）
/devloop-setup init         # 初回セットアップ
/devloop-setup repair       # 欠落設定の修復
/devloop-setup reconfigure  # 設定の更新
```

**機能：**
- 🔎 技術スタックを自動検出（言語、フレームワーク、パッケージマネージャー、テスト/Lint/ビルドコマンド）
- 🗺️ ソースディレクトリをスキャンし、L0 アーキテクチャマップを構築
- 📁 `devloop/` ディレクトリ構造を作成
- ⚙️ OpenSpec 設定を初期化
- 📝 検出値で設定ファイルを生成
- 🔁 冪等——複数回実行可能

### `devloop` — 開発

要件を完全な開発ループで駆動します。

```text
/develop ダークモードサポートを追加したい
/develop ログインリダイレクトのバグを修正
/develop 決済モジュールをイベント駆動アーキテクチャにリファクタ
/develop 全サービスにマルチテナント分離を追加
```

**機能：**
- 💾 `devloop/.state/` のチェンジごとの状態ファイルを読み込み、中断した作業を再開
- ⚖️ エスカレーション要因に基づくリスク分類（L0-L3）
- 🔥 ユーザーにヒアリングし、すべての決定分岐を解決
- 📄 OpenSpec チェンジアーティファクトを作成（proposal、specs、design、tasks）
- 🧪 TDD で実装
- ✅ スペックに対して検証
- 👁️ コード品質をレビュー
- 📦 正式スペックをアーカイブ・同期
- 📊 デリバリーレポートを出力

## 🚀 クイックスタート

### 1. DevLoop skill をインストール

**オプション A — `npx skills` でインストール（推奨）**

```bash
npx skills@latest add Mr-Poole3/devloop
```

CLI が `devloop-setup` と `devloop` の両方の skill を自動検出し、どのエージェントにインストールするか選択できます（Claude Code、Codex、OpenCode、TRAE、Cursor など 50+ 対応）。

個別の skill をインストールすることも可能：

```bash
npx skills@latest add Mr-Poole3/devloop/devloop-setup
npx skills@latest add Mr-Poole3/devloop/devloop
```

### 2. プロジェクトでセットアップを実行

```text
/devloop-setup init
```

`devloop/` ディレクトリが作成され、技術スタックが検出され、すべての設定が生成されます。

### 3. 開発を開始

```text
/develop <あなたの要件>
```

これだけです。残りは DevLoop が処理します。🎉

## ⚖️ リスクレベル

DevLoop は各要件をリスクレベルで自動分類し、適切なワークフローの重さを選択します。

| レベル | トリガー | ワークフロー | 確認ポイント |
|--------|---------|-------------|-------------|
| **L0** | コードの動作変更なし（ドキュメント、コメント、設定の修正） | 直接処理 | なし |
| **L1** | 単一モジュール・低リスク修正 | `diagnose → tdd → review` | 開始、完了 |
| **L2** | 中機能またはリファクタ | `grill → OpenSpec → apply → verify → archive` | 要件、計画、アーカイブ |
| **L3** | クロスモジュール・高リスク・アーキテクチャ変更 | `grill-with-docs → explore → spec/tickets → OpenSpec → apply → verify → review → archive` | 要件、計画、コーディング開始、アーカイブ |

**🚨 エスカレーション要因**（以下のいずれかで最低 L2 に昇格）：

- データモデルの変更
- 公開 API の変更
- 権限、決済、プライバシー、ユーザーデータ
- データマイグレーション
- クロスサービスまたはクロスモジュールの影響
- 後方互換性の要件
- ロールバック要件
- 高い技術的不確実性
- 複数人または複数エージェントの協力

## 📁 ディレクトリ構造

`devloop-setup init` の後、プロジェクトに `devloop/` ディレクトリが作成されます：

```text
your-project/
├── devloop/                        # DevLoop の全アーティファクトはここに
│   ├── config.yaml                 # DevLoop 総合制御設定
│   ├── .state/                     # 変更ごとの実行状態（gitignore 対象、並列複数変更対応）
│   │   └── <change-id>.yaml        # 進行中の変更ごとの状態ファイル（schema_version: 1）
│   ├── context/                    # プロジェクトコンテキストとアーキテクチャマップ
│   │   ├── architecture-map.md     # L0 モジュールインデックス（高速構造スキャン）
│   │   ├── tech-stack.md           # 検出された言語、フレームワーク、コマンド
│   │   ├── module-index.yaml       # モジュール仕様追跡（has_spec フラグ）
│   │   └── CONTEXT.md              # ドメイン言語とビジネスコンテキスト
│   ├── decisions/                  # アーキテクチャ決定記録（ADR）
│   ├── research/                   # 調査ノートとドラフト提案
│   ├── tickets/                    # タスク分割出力
│   ├── reports/                    # 検証レポートとデリバリーサマリー
│   └── openspec/                   # OpenSpec ネイティブディレクトリ
│       ├── config.yaml             # OpenSpec アーティファクトルールとコンテキスト
│       ├── specs/                  # アーカイブされた正式動作仕様
│       └── changes/                # 進行中のチェンジ
│           └── archive/            # 完了チェンジの履歴
├── src/                            # ソースコード（変更なし）
├── package.json                    # プロジェクトマニフェスト（変更なし）
└── ...
```

**ファイル管理ルール：**
1. 正式な決定はスクラッチに置かない——`CONTEXT.md`、ADR、または OpenSpec に移行。
2. 各情報は正確に一つの主ファイルを持つ——他は参照し、複製しない。
3. ファイルライフサイクルは明確——一時ファイルはクリーンアップ可能、進行中のチェンジは `changes/`、完了後はアーカイブ。

## 🔄 ライフサイクル

DevLoop は 10 段階の状態マシンに従います。段階は固定フェーズではなく、再訪可能なアクションです。

```text
intake          要件を受信、プロジェクトコンテキストを読み込み
triaging        リスクレベルを分類（L0-L3）
exploring       アーキテクチャマップを読み込み、欠落モジュール仕様を構築（L1 オンデマンド）
grilling        要件を明確化（L2 は grill-me、L3 は grill-with-docs）
specifying      OpenSpec チェンジを作成（proposal、specs、design、tasks）
reviewing_plan  ⏸️ [確認] 要件 + 計画サマリーを提示（L2 ファストトラックは combined_plan に統合）
implementing    ⏸️ [L3/hotfix 確認] TDD でタスクを実行、スペックファースト
verifying       テスト、/opsx:verify、コードレビューを実行
archiving       ⏸️ [確認] スペックを同期、チェンジをアーカイブ、モジュールインデックスを更新（hotfix は遡及スペック必須）
done            デリバリーレポートを出力 📦
```

**後方遷移が可能：**
- `implementing → specifying`：スペックのギャップを発見
- `implementing → exploring`：コードベース構造が不一致
- `verifying → implementing`：検証でコード問題を発見
- `verifying → specifying`：検証でスペック問題を発見

## ⏸️ 確認ポイント

高自動化モードでも、DevLoop は致命的なミスを防ぐために重要なポイントで一時停止します。

| ポイント | タイミング | 提示内容 |
|---------|---------|---------|
| **要件理解** | ヒアリング後、スペック作成前 | 目標、ユーザー、スコープ、成功基準、決定事項、不確実事項 |
| **計画とスペック** | OpenSpec アーティファクト生成後、コーディング前 | Proposal、specs、design、tasks、テスト戦略、リスク、ロールバック |
| **統合計画**（L2 ファストトラック） | 要件と計画を一括確認 | 要件サマリーと計画サマリーをまとめて提示 |
| **コーディング開始**（L3 または hotfix） | 最初のコード変更前 | 変更ファイル、新規ファイル、テストファイル |
| **最終アーカイブ** | 検証後、アーカイブ前 | デリバリーサマリー、テスト結果、検証結果、警告 |

## 📐 スペックファースト原則

```text
この変更は外部動作やアーキテクチャに影響しますか？
  はい → まず OpenSpec を更新、それからコードを変更
  いいえ → 直接コードを変更、デリバリーサマリーに記録
```

これにより、スペックドリフト——コードとスペックが時間とともに乖離し、`/opsx:verify` が無意味になる事態——を防ぎます。

## 🏗️ ブラウンフィールド戦略：構造化インデックス + オンデマンドモデリング

DevLoop は新規プロジェクトを必要としません。既存コードベースには三層アプローチを使用します：

```text
L0 — アーキテクチャマップ（セットアップ時）
     高速構造スキャン。モジュール、パス、責任、依存関係を記録。
     動作仕様なし。深い分析なし。数分で完了。

L1 — オンデマンドモジュール仕様（初回タッチ時）
     チェンジが初めて has_spec: false のモジュールにタッチした際、
     DevLoop がそのモジュールを深く調査し、動作仕様を構築。
     この仕様は以降のすべてのチェンジで再利用可能。

L2 — 継続的メンテナンス（アーカイブ時）
     各アーカイブされたチェンジは、差分スペックを正式レジストリに自動同期。
     構造が変更された場合、モジュールインデックスとアーキテクチャマップを更新。
```

つまり、スペックカバレッジは実際の開発活動とともに自然に成長します——無駄な事前ドキュメントはありません。🌱

## 💾 状態復旧

DevLoop は変更ごとの状態ファイル `devloop/.state/<change-id>.yaml`（gitignore 対象）でセッション横断の復旧を管理します。レガシー `devloop/.state.yaml` は初回読み込み時に自動移行されます。

```yaml
# devloop/.state/<change-id>.yaml
schema_version: 1
change_id: add-dark-mode
stage: implementing
risk_level: L2
fast_track: false
hotfix: false
confirmed: [requirement_understanding, plan_and_spec]
pending_confirmation: []
tasks:
  total: 12
  completed: 7
  current: "2.3 Update theme toggle component"
consecutive_failures: 0
metrics:
  stage_durations: { intake: 2s, triaging: 5s, grilling: 120s }
  failure_counts: { test: 1, typecheck: 0, lint: 0, verify: 0 }
  confirmation_rejections: 0
  spec_drifts: 0
created_at: "2026-08-01T10:00:00Z"
last_updated: "2026-08-01T10:30:00Z"
```

再開時、DevLoop は進行中の状態ファイルを読み込み、**継続 / 並列で新規作成 / 破棄？** と尋ねます。

## 🛡️ 障害復旧

| エラータイプ | 復旧戦略 |
|---|---|
| テスト失敗 | `diagnosing-bugs` skill に入る——再現、最小化、仮説、計測、修正、回帰テスト |
| 型チェック/Lint 失敗 | 直接修正；3 連続失敗で一時停止 |
| OpenSpec CLI 失敗 | 設定またはアーティファクト形式を修正してリトライ；CLI をバイパスしない |
| `/opsx:verify` の不一致 | 各問題を分類し、コードまたはスペックを修正、再検証 |
| コードベース構造の不一致 | `exploring` に戻り、再調査 |
| **3 連続失敗** | **🚨 強制一時停止**——診断レポートを出力、ユーザーの介入を要求 |
| ユーザー中断 | 状態を保存、ハンドオフサマリーを出力 |
| 依存関係の欠落 | 一時停止して報告、代替案を試みない |

## ✅ 三層完了基準

チェンジは三層すべてがパスした場合のみ完了です：

```text
コード層     🧪 テスト + 型チェック + Lint + ビルド
スペック層   📋 /opsx:verify: 0 クリティカル
デリバリー層 📦 タスク + コードレビュー + デリバリーサマリー
```

### テスト基準

| レベル | カバレッジ要件 |
|--------|--------------|
| **L1** | バグシナリオをカバーする少なくとも 1 つの回帰テスト |
| **L2** | すべての OpenSpec specs シナリオに対応するテスト |
| **L3** | すべてのシナリオ + クリティカルなクロスモジュール結合テスト |

**クリティカルドメイン**（セキュリティ、データ、決済、プライバシー）は、リスクレベルに関わらず専用テストが必要です。

**主要ルール：**
- テストはプロジェクトの慣習に従う：既存のテストディレクトリと `*.test.ts` 命名。
- テストは外部から観測可能な動作を検証し、内部実装の詳細は検証しない。
- 根本原因を確認せずにテストアサーションを変更して通過させてはならない。
- テストは実装コードと同じ OpenSpec change で提出する。
- テスト失敗はハードゲート——アーカイブのためにスキップやバイパスは不可。

## 🖥️ ホスト互換性

DevLoop はホスト固有機能に依存せず、能力検出で複数 AI コーディングホストに対応します。

| 能力 | 用途 | 不可時の動作 |
|------|------|------------|
| サブエージェント/並列ワーカー | 並列 code-review、並列 verify | 同処理を直列実行 |
| バックグラウンドタスク | 非ブロッキング verify + review pipeline | 明示的ステージゲートの同期パイプライン |
| 自動 skill トリガー | intake 時の `/develop` 自動実行 | ユーザーが `/develop` を手動呼び出し |
| ワークスペースFS連携 | 同リポジトリ内エージェント間状態共有 | ロック＋単一ライター更新 |

**対応ホスト（能力認識）：**

| ホスト | 状態 | 能力メモ |
|--------|------|----------|
| Claude Code | ✅ 完全 | サブエージェント、バックグラウンドタスク |
| Codex | ✅ 完全 | 能力検出が必要 |
| OpenCode | ✅ 完全 | 能力検出が必要 |
| TRAE | ✅ 完全 | 能力検出が必要 |
| Cursor | ✅ 完全 | 能力検出が必要 |
| その他 | 🟡 部分 | 手動オーケストレーションで利用可能 |

**デグレードルール（ホスト非依存）：**
- サブエージェント未対応 → `code-review` は直列実行
- バックグラウンドタスク未対応 → 非同期パイプライン無効
- 自動トリガー未対応 → ユーザーが手動で `/develop` を呼び出し
- OpenSpec CLI なし → L0/L1 のみ；L2/L3 は一時停止しインストール手順を表示

| 依存関係 | 必要な場面 | インストール |
|---------|-----------|-------------|
| [OpenSpec CLI](https://github.com/Fission-AI/OpenSpec) | L2/L3 完全ワークフロー | `npm install -g @fission-ai/openspec@latest` |
| [mattpocock/skills](https://github.com/mattpocock/skills) | ヒアリング、TDD、デバッグ、コードレビュー | `npx skills@latest add mattpocock/skills` |

DevLoop は依存関係なしで L0/L1 タスクを処理できます。L2/L3 は一時停止し、欠落依存関係を報告します。

---

## 💡 主要原則

1. **単一エントリポイント**——ユーザーは要件を提供するだけ。手動オーケストレーション不要。
2. **実行前に理解**——コードを書く前にヒアリングを行う。
3. **OpenSpec が真実**——現在のチェンジの proposal、specs、design、tasks が唯一の実行権威。
4. **Skills は機能**——ヒアリング、TDD、デバッグ、レビューは組み合わせ可能なツールであり、固定フレームワークではない。
5. **リスクが重さを決定**——小さな修正は軽量に；大きな変更は完全処理。
6. **実装はロールバックを許可**——新しい情報はコード前にスペックを更新。
7. **完了は検証可能であるべき**——三層検証：コード、スペック、デリバリー。

---

## 🏛️ 権威階層

```text
CONTEXT.md / ADR              → 長期的なプロジェクト事実とドメイン言語
devloop/openspec/changes/     → 現在のチェンジの唯一の実行真実
devloop/openspec/specs/       → アーカイブされた正式動作仕様
Issue Tracker                 → チーム調整、担当者、スケジューリング
Code & Tests                  → 実際の実装
```

ドキュメントが競合する場合：**現在の OpenSpec チェンジが優先**。ただし、競合はデリバリーサマリーに報告必須。

---

## 🤝 コントリビュート

貢献を歓迎します。重要な変更については、DevLoop ワークフロー自体に従ってください：

1. フォークで `/devloop-setup init` を実行
2. `/develop <あなたの改善>`
3. 三層検証がパスすることを確認
4. デリバリーサマリーを添付して PR を提出
